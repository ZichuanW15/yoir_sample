# US-02 backend: secure account creation

Issue: [#93](https://github.com/swen90014-2026-sm2/SWEN90014-2026-CSD-Koala/issues/93),
under [US-02 #5](https://github.com/swen90014-2026-sm2/SWEN90014-2026-CSD-Koala/issues/5).

This slice completes the backend account-creation boundary behind the existing
registration form. It builds on [US-01's request contract](us01-registration.md)
and preserves the frontend/deployment changes merged from `dev` at `65db231`.
No new endpoint, response field, database column or dependency is introduced.

## Behaviour and integration

The public `POST /api/v1/auth/users` still accepts `name`, `email`, `password`,
`passwordConfirmation` and `role`. For this story, `role` is `job_seeker`;
the existing `counsellor` registration path remains supported for US-04.

- Required fields, trimmed name, email, password length, matching confirmation
  and supported role are validated on the server before hashing or account writes.
  Unknown fields, including caller-supplied hashes or verification flags, are rejected.
- Valid input creates one user with a generated ID, creation timestamp,
  normalised name/email and a salted password hash. Passwords are never trimmed.
- The response is built from the public `UserOut` fields before commit; HTTP `201`
  is returned only after commit succeeds. There is no post-commit refresh that could
  report a failure after the account has already been created.
- A failed write rolls back the transaction. Unrecognised failures propagate to the
  existing generic HTTP `500` error handler; email-uniqueness conflicts now return
  HTTP `409` through the [US-03 follow-up](us03-duplicate-email.md).
  A hashing failure also returns an error, without inserting
  an account. Internal exception details and credentials are not returned to the app.
- Registration returns only `id`, `name`, `email` and `role`: no JWT, cookie, password
  or password hash. Login remains a separate `POST /api/v1/auth/sessions` call.

The `dev` frontend's `api.register` and `auth/register.tsx` already use this contract:
they await the response, show the success screen and offer **Continue to log in**.
The backend does not redirect or create a session. Validation errors retain HTTP
`400` with English `message` and `fieldErrors`; ordinary duplicate emails retain
HTTP `409`. The database uniqueness-race behaviour is covered by the separate
[US-03 backend slice](us03-duplicate-email.md).

A transport failure while acknowledging a database commit can still leave the
outcome uncertain. This change removes the avoidable post-commit read; it does not
claim exactly-once registration or introduce an idempotency protocol.

## Design decision: password storage

Use the existing `argon2-cffi` dependency with the explicit
`RFC_9106_LOW_MEMORY` profile. This records the policy already used by the locked
library's defaults, rather than silently inheriting future default changes.
The [library documentation](https://argon2-cffi.readthedocs.io/en/stable/api.html#profiles)
describes the named profile and random-salt behaviour.

| Setting | Value |
|---|---|
| Algorithm | Argon2id, version 19 |
| Memory cost | 65,536 KiB (64 MiB) per hash |
| Time cost | 3 iterations |
| Parallelism | 4 lanes |
| Salt | 16 random bytes generated by the library for each hash |
| Hash output | 32 bytes |

Store only the encoded result in `users.password_hash`; it contains the algorithm,
parameters, salt and hash needed for later verification. Two accounts using the
same password receive different salts and hashes. No separate plaintext password
or confirmation field exists in the user table. Existing encoded Argon2 hashes
remain verifiable without rewriting account data.

Registration's Pydantic `str`/`repr` omit both credential fields. This is defence
against accidental debug logging, not blanket log redaction: code must still not
log request bodies, explicit model dumps or SQL parameters containing credentials.
Deployment memory/concurrency should be measured before changing hashing cost;
this task does not lower the current policy or add a new password-validity rule.

## Verification and hand-off

Use the updated `dev` setup (Python 3.12, `uv.lock`) from `backend/`:

```bash
uv sync --locked
uv run --no-sync pytest tests/test_account_creation.py
uv run --no-sync pytest tests/test_api.py -k register
uv run --no-sync pytest tests/test_registration_contract.py
uv run --no-sync pytest tests -m "not live"
uv run --no-sync ruff check app tests reset_db.py
```

With `DATABASE_URL` unset, the harness creates its own temporary SQLite database;
it does not use the developer's `.env` database. PostgreSQL tests must use a dedicated
test database and the existing explicit QA reset guard, as documented in the
[test approach](../../sprint1/qa/test-approach.md).

`backend/tests/test_account_creation.py` provides backend evidence for
**AT-US-02-1** and **AT-US-02-2**: independently persisted hash-only accounts,
recorded Argon2 parameters, per-account salt, Unicode/whitespace password round-trip,
separate login, no token issuance during registration, validation before hashing,
safe hashing/write failures, explicit rollback and response independence from a
post-commit read. US-01 tests retain the required-field and public-contract coverage.

At this slice's verification time, the US-03 strict-XFail test double supported the
flush/rollback boundary without claiming the 409 race fixed. The US-03 follow-up
replaces it with an actual database-conflict regression and removes that XFail.
The historical results below describe the US-02 baseline before that follow-up.

Frontend task #92 is already closed on GitHub. Device recordings and independent
QA sign-off remain with [#94](https://github.com/swen90014-2026-sm2/SWEN90014-2026-CSD-Koala/issues/94).
This backend implementation alone does not close parent story #5.
